# ADR-012: 開発の指針と採用基準

- **日付**: 2026-11-28
- **状態**: Accepted
- **決定者**: 決定 1〜4 はリポ所有者。決定 5〜7 は作業エージェント(Claude)が戻せる範囲で決め、所有者がこの記録のマージで承認する

## 背景

open Issue の多くが「方針が決まっていない」ことを理由に止まっていた。
1 件ずつ決めると判断がぶれるので、止まっていた判断から共通の指針を取り出して記録する。
指針は、実際に判断が要った箇所から取り出したものだけに限る(先回りした規則は足さない)。

この記録は「何を目指すか」を定める。ここに書いた挙動の実装は、それぞれの Issue で行う。
実装が済んでいるかどうかは、この記録からは読み取らない。

## 指針

判断が割れたときは、上にあるものを優先する。

1. **正しさ**: 結果が eager(PyTorch 標準)と一致すると確かめられない候補は採用しない。確かめられないときは eager で実行する。
2. **既定で害がない**: `@forge.optimize` を付けただけで遅くなる状態を作らない。
3. **速さ**: 1 と 2 を満たした上で、速い候補を採る。
4. **探索の幅**: 新しい探索方法は、1〜3 を崩さない形で足す。

加えて、進め方について次を守る。

- **測ってから設計を変える**: 既存の ADR を覆す提案は、公開 API にしない実験として実装し、実測してから ADR を改訂するかを決める。
- **信頼の境界を書く**: 何を信頼し、どこで隔離するかを文書に書く。検査の名前から、実際より強い保証を読み取れる状態にしない。
- **文書と実装が食い違うとき**: 利用者がいる挙動は実装に合わせて文書を直すか、実装を直すかを決める。利用者がいない機能は、配線せず文書を直す。
- **足す前に削る**: 仕組みを足すのは、無いことで困った実績があるときだけにする。

## 決定

### 1. 採用基準: eager に `min_speedup` 倍で勝たなければ採用しない

探索で最良だった候補が、eager に `min_speedup` 倍(既定 1.03)で勝たなければ採用しない。
キャッシュにも書かず、eager で実行する。判定には、探索中に集めた baseline の計測値を使う。

- 指針: 2(既定で害がない)
- 却下した案: 1.0 倍で固定する(計測のばらつきで採否が揺れる)。遅い候補も採用して警告だけ出す(付けたら遅くなる状態が残る)
- 戻し方: `min_speedup` を下げると、従来の挙動に近づく
- 補足: README のベンチマーク表は、採用の可否とは別の「報告用の計測結果」として残す

### 2. LLM によるコード全体の生成: ADR-005 は変えず、実験で先に測る

[ADR-005](ADR-005-structured-llm-generation.md)(LLM はパラメータだけを提案し、コードはテンプレートが生成する)は変えない。
LLM にカーネルのコード全体を書かせる方式は、公開 API にしない実験経路として実装し、
パラメータ探索との比較を実測してから、ADR-005 を改訂するかを決める。

- 指針: 測ってから設計を変える
- 条件: 実験経路でも、生成コードは決定 7 の検査を必ず通し、実行は [ADR-003](ADR-003-subprocess-isolation.md) の subprocess で行う
- 却下した案: 実測を待たずに ADR-005 を改訂して公開 API にする(生成コードを実行する前提が安全性の土台になり、戻しにくい)。提案を閉じる(比較の数字が無いまま決めることになる)
- 戻し方: 実験経路は公開 API ではないので、削除すれば戻る

### 3. キャッシュの信頼: 署名鍵を永続化し、署名は実行に使う入力すべてを覆う

SQLite キャッシュ([ADR-002](ADR-002-sqlite-cache.md))を別のプロセスからも再利用できるように、署名鍵をユーザーのホーム配下に保存する。
前提は次のとおりとする。

- 信頼するもの: 同じ OS ユーザーのホーム配下(鍵ファイルとキャッシュ DB)。同じユーザーの権限で動く別のプログラムからは守らない
- 署名が守るもの: キャッシュ DB だけが書き換えられた場合(共有・コピー・破損を含む)
- 署名の範囲: カーネルの実行に使う入力すべて(保存したコードだけでなく、コードを作り直す元になるパラメータとキャッシュキーを含む)
- キャッシュから読んだパラメータは、信頼せず型と範囲を検証する

- 指針: 信頼の境界を書く
- 却下した案: プロセスごとの鍵のままにする(別プロセスでは必ずキャッシュミスになり、永続キャッシュの目的を果たせない)。署名の方式を作り直す(前提を上のとおり書けば足りる)
- 戻し方: 鍵ファイルを消すと既存のエントリはすべて検証に失敗し、再探索になる

### 4. リポの役割: 開発は公開リポで行う

開発・Issue・リリースを公開リポ 1 つにまとめ、非公開の開発用リポは移行後に archive する。

- 指針: 足す前に削る(2 つのリポを同期する仕組みを作らない)
- 影響:
  - 未修正の脆弱性の詳細は、公開の Issue・PR に書かない。GitHub の security advisory(非公開)で扱う
  - 公開リポの CI は GitHub-hosted runner で動く(組織の CI 規約による)
  - 移行の前に、安全性に関わる修正(決定 3・7)を済ませる
- 却下した案: 非公開リポで開発し、節目ごとに公開側へ同期する(二重管理になる)
- 戻し方: archive は解除できる。公開した内容は取り消せないので、公開側へ入れる差分は入れる前に点検する

### 5. コストガード([ADR-011](ADR-011-cost-aware-search.md))は探索ループに配線しない

ADR-011 の部品(`CostModel`・`BudgetTracker`・`scalarize`)は残すが、探索ループには配線しない。
ADR-011 の「影響」は、配線されていない現状に合わせて書き直す。

- 指針: 文書と実装が食い違うとき(利用者がいない機能は、配線せず文書を直す)
- 却下した案: 探索ループに配線する(必要とする利用の実績がない)
- 戻し方: 必要になった時点で配線し、ADR-011 を戻す

### 6. Python 依存の lock ファイルは持たない

lock ファイルは置かず、開発用の依存に上限を付ける。

- 指針: 足す前に削る
- 理由: CI は組織共通の workflow から pip で依存を入れるため、lock を置いても CI では使われない
- 却下した案: lock ファイルを追加する(CI と開発環境で依存の解決方法が分かれる)
- 戻し方: CI が lock を読む構成になった時点で追加する

### 7. 生成コードの AST 検査はサンドボックスではない

生成コードの AST 検査は、明らかに危険な記述を早く弾くための前段であり、隔離の手段ではない。
隔離の線は [ADR-003](ADR-003-subprocess-isolation.md) の subprocess とする。
検査は禁止リストを強化して続けるが、これだけで安全とは扱わない。

- 指針: 信頼の境界を書く
- 却下した案: 許可するモジュールを絞り込んでサンドボックスとして扱う(既存のテンプレートが `torch` を import しており、AST 検査だけでは保証できない)
- 戻し方: 該当なし(位置づけの明記)

## 再検討条件

- 決定 1: 既定の `min_speedup` で、明らかに速いカーネルが不採用になる例が続いたとき
- 決定 2: 実験経路での比較の実測が出たとき
- 決定 3: 複数ユーザーでキャッシュを共有する使い方が出てきたとき
- 決定 4: 公開リポの CI が長く止まり、開発が進まなくなったとき
- 決定 5・6: 「戻し方」に書いた条件が成り立ったとき
